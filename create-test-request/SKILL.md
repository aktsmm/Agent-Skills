# 検証タスクとテスト依頼文を作成

現在の会話、選択範囲、開いている資料、workspace内の成果物から検証タスクを抽出し、別の検証workspaceのエージェントへ貼り付ける自己完結したテスト依頼文を作る。設定の読み取り確認も対象に含む。このskillを実行するセッションでは検証・構築・設定変更を行わず、依頼文だけを生成する。

## 実行境界と応答フェーズ

- このskillを実行するセッションでは、読み取り・検索・状態確認以外の操作を行わない。handoff生成前も検証対象を変更しない。
- **第1応答**: `ask_user` を1回だけ使い、次の2項目を同じフォームで確認する。handoff本文はまだ生成しない。
  - **検証の目的**: 会話と成果物から目的を1文で推定し、`はい、この目的でhandoffを作成` または自由入力での訂正を受け付ける。変更を伴う場合は、専用環境か、作成・変更・削除、承認カード、権限・モード変更の許可範囲も目的と一緒に確認する。
  - **検証後のコピー先（任意）**: 原本は検証workspaceに残し、報告文・主要スクリーンショット・結論を裏付ける証跡だけをコピーする旨を示す。選択肢は `提案先にコピーする（推奨）`、`別の場所にコピーする`、`コピー不要`。提案は検証側が書き込めて依頼側が閲覧できると確認済みの場所に限り、既存の共有workspaceを優先し、使えなければ既知のSharePointフォルダーを検討する。提案できる場合だけフォルダー名とリンクを示して推奨を出す。別の場所は共有workspaceのフォルダーまたはSharePointのフォルダーURLを指定してもらい、推測で補わない。
- 回答・訂正を検証目的とコピー先の正本とする。コピー先の未回答・未確定だけでは目的承認後のhandoff生成を止めない。
- ユーザーが目的の不足・狭さ・誤解を指摘した場合は、訂正文だけへ置換しない。会話と成果物を再確認し、指摘された観点を検証対象、構築・変更手順、証跡、rollback、cleanup、完了条件へ再統合した目的文を作る。
- 目的を訂正したときは、確定済みのコピー先を聞き直さず、同じフォーム形式で目的を再確認する。目的の明示承認前に第2応答へ進まない。目的以外の指摘は再確認せず、反映したhandoff全文を再出力する。
- **第2応答**: 確認済みの目的を反映したhandoff全文を、単一の`markdown` fenced blockだけで出力する。ブロック外に前置きや補足を書かない。

## 入力の確定

- 優先順位は `最新のユーザー指示 > 現在の成果物と検証結果 > 会話中の計画 > 古い仮説` とする。
- まず対象資料、検証対象、現時点の設計判断、未確認事項、対象環境、変更可能範囲を特定する。
- workspace内に元資料があれば、会話の要約より実ファイルを優先して読む。
- 未取得のsubscription、resource、tenant、region、SKU、権限、接続情報は推測せず`<要確認>`とする。secret値はhandoffへ書かない。
- 第1応答のフォームは目的とコピー先に限る。他の不足情報はhandoffの`Environment`または`First Response Contract`に`<要確認>`として含め、受け手側で確認させる。

## 生成するhandoffの開始ゲート

handoffを受け取ったエージェントへ、最初の応答ではtoolを実行せず、次だけを日本語で返すよう明記する。

1. `理解しました。今回の目的は...です。`
2. `実施することは次のとおりです。`として、検証項目を順序付きで要約する。
3. 確定済みの前提と不足情報を分ける。
4. 構築・設定変更・deploy・権限変更・削除が含まれる場合は、実行前に承認が必要な操作を列挙する。許可された範囲（下記）を示した依頼では、範囲内の操作を再確認なしで実施すると明記し、承認が必要なのは範囲外の操作だけにする。
5. `この理解と進め方でよければ、進めてくださいとお知らせください。`で止める。

ユーザーが`進めて`、`検証して`、または同等の明示承認を返すまで、読み取り確認を含むtool実行を開始させない。最新のユーザー指示が「受領後すぐ検証開始」と明示している場合だけ、この待機を省略できる。

## handoffに含める内容

### Goal

- 何を実環境で証明または反証するか。
- どの設計判断・仮説・構成候補を検証するか。
- 誰が判断に使う成果物か。

### Source of Truth

- 受け手が元資料を読める保証はない。検証に必要な主張・数値・手順・仕様の記述はhandoff本文へ全文で埋め込み、「資料を提供してください」と言わせない。fileの相対 path は、受け手のworkspaceに同じfileがあるとユーザーが確認した場合だけ使う。
- 公式仕様URLと、その仕様から導いた設計判断を分ける。
- 既に確認済みの事実、未確認、仮説を分類する。

### Environment and Safety Boundary

- 対象tenant、subscription、resource group、resource、region、SKU。未取得値は`<要確認>`。
- 認証が必要なことだけを理由に、アカウントや環境を検証範囲から外さない。ユーザー本人がサインインする確認点を入れて含める（パスワード・MFAは本人のみ）。
- read-onlyで確認できる項目と、変更を伴う項目を分ける。
- **許可された範囲**: 専用の非本番検証環境では、本人が許可した変更（resource作成・変更・削除、VM起動停止、エージェントや応答プランの設定・モード変更、範囲を限定した権限付与、承認カードの承認）を、再確認なしで実施してよいと書く。範囲は「専用のリソースグループと専用のエージェントの内側」のように具体的に限定し、変更前後の状態の記録とrollbackを条件にする。承認カードを承認する場合も、承認の前（内容: コマンド・パラメータ・スコープ）と後（結果）の画面を撮る。範囲外の破壊的操作を含むカードは承認しない。許可の範囲が未確認なら、従来どおり全変更を承認制にする。
- 承認制のとき（または範囲外）に禁止する操作: resource作成・変更・削除、deploy、権限付与、network/DNS変更、public access変更、secret取得・表示、共有process操作、push。許可された範囲があっても、secret取得・表示、push、範囲外のリソース・テナント全体の設定、並行して動いている別の試験への干渉は禁止する（干渉禁止の対象はhandoffに具体的に書く）。
- secretは環境変数・既存認証session・Key Vault等から取得し、保存・表示しない。

### Required Validation

検証項目を依存順に並べ、各項目へ次を付ける。

- 対象と確認方法
- 合格条件
- 失敗時に区別する仮説
- 保存する証跡
- 変更が必要な場合のrollback

最低限、該当する範囲で次を含める。

1. control planeとresource状態、SKU、region、権限。
2. network path、routing/peering、Private Endpoint、Private DNS、TLS。
3. 認証主体、tokenのissuer/audience/claim、managed identity、RBAC。
4. public accessを無効にした状態でのprivate経路成功。
5. producer単体、接続部品単体、end-to-endの順での切り分け。
6. timeout、response size、retry、重複処理、ログ・メトリクス。
7. negative testと、変更前へ戻せるrollback確認。

### Execution Phases

`Discovery → Read-only baseline → Change plan and approval → Minimal build/change → Component tests → End-to-end test → Rollback test → Cleanup → Report`の順にする。変更不要の検証では不要なphaseを省く。

### Evidence

- 作業中の原本は検証workspaceに保存し、移動・削除しない。検証後、コピー先が指定された場合だけ、共有可能な検証報告文・主要スクリーンショット・必要な証跡を選んで指定先へコピーする。フォルダー全体や未加工の記録は一律にコピーしない。
- `コピー不要` と `コピー先・アクセス未確認` を区別する。未指定・未確定、または検証側の書き込み・依頼側の閲覧を確認できない場合はコピーせず原本を残す。指定は共有範囲の変更や権限付与の許可ではない。
- 最終報告では、コピーしたファイルと確認済みのリンク、またはコピーしなかった理由と原本の所在を示す。実際に保存・確認できていないものをコピー済みと書かない。

### Completion Criteria

- 合格条件を結果と証跡で判定できる。
- 設定値や自己申告だけで完了にしない。
- 未確認項目は未確認の理由と次の確認条件を残す。
- 一時resource・一時script・一時権限のcleanup状態を明記する。
- 障害注入の検証では、注入の方法がログに残す痕跡（例: 管理操作の記録）を確認し、エージェントや監視の「一致」が痕跡に依存していないかを区別して報告させる。復旧しない設定（サービスの自動再起動など）は、注入前に確認させる。
- 最終報告に`Verified / Failed / Unverified`、実行したtool/CLI、証跡path、変更内容、rollback結果、残リスクを含める。

## 出力形式

第1応答で検証目的の確認が完了した後、次の順序で貼り付け可能なhandoff全文だけを単一の`markdown` fenced blockで出力する。

1. Title
2. First Response Contract
3. Goal
4. Background and Current Decision
5. Source of Truth
6. Environment
7. Required Validation
8. Execution Phases
9. Evidence
10. Completion Criteria
11. Must NOT（許可された範囲があれば、その範囲外の操作に絞る）
12. Final Report Format

handoff本文に内部推論、不要な会話履歴、顧客の個人情報、secret、ローカル絶対パスを含めない。元資料は本文へ埋め込み、file参照に依存させない。
