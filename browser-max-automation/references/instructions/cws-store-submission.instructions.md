# CWS Submission In An Authenticated Browser

Use a verified authenticated CWS tab for listing/privacy fields and Dashboard state. Prefer API/CLI for token validation, package upload and publish when available; combine them with UI readback rather than forcing one route to do everything.

1. Pin one browser process, top-level window, selected address-bar value, publisher route, and item ID. Exclude unrelated browser sessions by PID, `user-data-dir`, and URL. Do not restart the browser, copy a profile, or handle credentials.
2. Attach Windows UI Automation read-only first. If browser chrome appears without `RootWebArea`, verify that the exact CWS page has no unsaved work, invoke Reload once, and require `RootWebArea` before any write.
3. Use `ValuePattern`, `InvokePattern`, `ExpandCollapsePattern`, and `TogglePattern`; do not use coordinates, OS keystrokes, or the clipboard. Re-resolve controls after each SPA update because automation IDs can change.
4. An upload button may first open an in-page ZIP/CRX dialog rather than a native file chooser. Resolve its single file input and select the hash-verified artifact once; a missing chooser event alone is not grounds to click upload again. For a native chooser, require the visible `Open` dialog owned by the pinned browser with its window disabled, then select the verified artifact.
5. CWS image deletion has a separate confirmation. Delete and confirm one image at a time. A multi-file choice may add only its first image, so upload remaining screenshots individually and verify the count after each upload.
6. For Privacy, classify every data checkbox from implemented feature/schema/payload/listener evidence. Local-only handling still requires disclosure, but do not equate requested browser actions with behavioral monitoring or incidental page contents with dedicated category collection. Save, navigate away/back, and re-read every checkbox, attestation, remote-code choice, purpose/permission field and policy URL.
7. For Listing, save then navigate away/back and compare descriptions/URLs and required media state. If a filled field reverts after reload, retry once with per-character browser input events on the pinned field, then save and reread; do not replay Submit on a transient value. Recheck package version separately; listing save does not prove ZIP upload.
8. Before submit, verify the expected DRAFT version in API and Dashboard package views. Sparse API values such as `uploadState: NOT_FOUND` or null error elements do not override a matching draft version plus a successful upload; record each signal.
9. A first **Submit for review** may open a confirmation or may be ambiguous. The Package tab header only offers the upload button; after an upload the page moves to the Store listing tab, whose header shows **Submit for review**. Verify product/version/auto-publish before confirmation, and read the header status badge afterwards (toasts keep past results). A second review-delay warning (e.g. broad host permissions) may follow; read and confirm it once before checking the item's version and pending-review status. If UI readback proves non-application and an authenticated publish API exists, switch once; never replay both routes speculatively.
10. Completion requires API publish acceptance plus Dashboard **Pending review/審査待ち**. Keep upload, draft/listing/privacy save, submission, review approval and public availability as separate states. Do not resubmit while review is pending or because the public page still shows the prior version.

For API credentials: the legacy v1.1 OAuth flow stopped on 2026-10-15, so `invalid_grant` there is not fixed by reauthorizing. Use the v2 service-account route instead (service account email registered in the Dashboard under Settings → service accounts, short-lived token by impersonation, no key file); the user's Dashboard login is the only manual step. Keep the same verified ZIP, and never send auth codes/tokens through chat. When the user does not answer a login request, leave the dedicated window at the login page and watch only the tab URL (`/json/list`, bounded, no page text) until the Dashboard URL appears or the user reports back. This workflow does not make browser automation or UIA a security boundary. Stop on an ambiguous account, publisher, item, modal, control, or post-write state.
