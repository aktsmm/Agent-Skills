# Teams AI議事録 → 議事録変換

## 📋 実行手順

### Step 0: 受領原文の保存

お客様・会議参加者から新規に提示されたメモ本文は、変換・要約・質問への回答より先に原文として保存する。

1. 会議日が分かる場合は `_received/mtg-YYYY-MM-DD-{topic}/`、不明な場合は `_received/incoming/` に保存する。
2. Preserve source wording, symbols, and paragraphs, except credentials and token-bearing image URLs; omit those and record the omission without sensitive values. Do not substitute a summary for the source.
3. `attachments.md` に出どころ・機密区分・関連議事録を記録し、議事録から原文へリンクする。

### Step 1: 日付の決定

ユーザー指定、対象会議の日時表示（recap・招待等）の順に採用し、いずれもなければ今日の日付を使う。次回予定、チャットの発言日、資料更新日は対象会議日と区別する。

### Step 1.5: ファイル確認と連携判定

1. **現在開いているファイルを確認** (`editorContext`)
2. ファイル名から日付を抽出（例: `meeting-notes/2026-02-04_sr-review.md` → `2026-02-04`）
3. **入力データの日付と比較**：
   - **一致**: 通常の変換処理（Step 2 へ）
   - **不一致（入力が過去）**: 「前回持ち帰りを次回に反映」と判断
     - 入力データから「フォローアップ タスク」を抽出
     - 現在開いているファイルの「🔄 前回持ち帰り事項の確認」に反映
     - **ユーザーに確認**: 「入力は{入力日付}のメモですが、開いているファイルは{ファイル日付}です。前回持ち帰りとして反映しますか？」

### Step 2: 会議種別と保存先の決定

`meeting-notes/` 直下に 1 会議 1 ファイルで作成または更新する。日付だけでなく会議名・リンクも照合し、同日別会議と混ぜない。

- 会議名・入力から内部のみと明確な会議や準備会、ユーザー指定、または内部情報を同一ファイル内で安全に分離できない場合: `meeting-notes/{YYYY-MM-DD}_{topic}_internal.md` を `assets/internal-memo.md` から作成する。
- それ以外または会議種別が不明な場合: `meeting-notes/{YYYY-MM-DD}_{topic}.md` をスキル同梱の `assets/meeting-minutes.md` から作成する。
- 未確定の技術条件、構成、費用、担当だけを理由に `_internal.md` を作らず、本文に `要確認` として残す。顧客共有用ハイライトには未確定事項を含めない。
- 同じ日付に内部用と共有用の記録がともに必要な場合だけ、両方を作る前にユーザーへ確認する。

### Step 3: 議事録変換

Teams AI議事録を以下のルールで変換：

| Teams AI形式               | テンプレート                 |
| -------------------------- | ---------------------------- |
| 会議のメモ: [トピック]     | 📝 議事内容 → トピックN      |
| トピック詳細（インデント） | ディスカッション             |
| フォローアップ タスク      | 🚀 今回の持ち帰り事項（NEW） |
| 担当者が自社名             | 自社 持ち帰り                |
| 担当者がお客様名           | お客様 持ち帰り              |

### Step 3.5: WorkIQ で補足（依頼がある場合）

- 受領原文を保存してから、対象会議・案件、関係者、期間、確認したい論点に絞り、Teams・メール・招待・資料を読み取り照会する。少数の根拠（原文リンク、発言者/送信者、日時とタイムゾーン、短い要点）を求める。
- `WorkIQ 補足` は会議時点の議事と分ける。採用した情報の根拠リンクを共有境界内に残し、原文を読めたか明記する。生成要約は探索の手掛かりで、逐語引用や独立した裏取りに使わない。顧客の発言を社内チャットで知った場合は「社内担当者の説明」と明示する。
- 担当・期限・合意・進捗を更新する前に原文や正本を確認する。準備会と本番、招待・承諾と実出席、工数の依頼・見積と正式割当、社内リンク共有と顧客送付・閲覧権限は別々に判定する。矛盾や取得不能は `要確認`（候補・確認先・未取得理由）とし、権限拒否は迂回しない。

### Step 4: 議事録と質問・アクションの保存

変換結果を Step 2 で決めた `meeting-notes/{YYYY-MM-DD}_{topic}.md` または `meeting-notes/{YYYY-MM-DD}_{topic}_internal.md` に保存する。

フォローアップ、未回答、確認依頼を `_questions/{YYYY-MM}.md` に、具体的な作業を `next-actions/` の既存の区分とタスク形式に沿って記録する。同じ項目は重複登録せず、確認できた状態・回答だけ更新する。任意案や社内準備は顧客合意の宿題にしない。既存の状態を変更する根拠がなければ据え置き、新規の状態が未確認なら注記にとどめる。抽出対象がなければ議事録のみ保存する。

### Step 4.5: 案件への紐付け

- 保存後、`workstreams/README.md` と各案件 README の名称、判定キーワード、現在の範囲を照合する。
- 既存案件が 1 件に明確に一致した場合は、確認済みの差分だけを案件 README に反映し、議事録へリンクする。関連するタスク・質問台帳・ポートフォリオの担当・状態・次の条件が一致するか読み戻す。議事録全文は複製しない。
- 新規、複数該当、または低確信の場合は、`workstreams/_candidates.md` に候補として記録して確認する。案件フォルダは確認後にだけ作成する。

### Step 5: Meeting URL Check

After saving the note and ledger, ask whether a Teams meeting, recap, or recording URL is available if none was supplied. Record supplied links in the existing note without asking again; distinguish saving a URL from accessing or verifying the full recording/transcript.

## 📝 変換ルール詳細

### 1. 基本情報

- **日時**: ファイル名の日付から `2026/01/21` 形式に変換
- **出席者**: 原文で出席を確認できる人だけを記載し、名前への言及だけでは出席者と断定しない。

### 2. 議事内容

- Teams AIの「会議のメモ:」の各トピック（コロン前）を `### トピックN: [タイトル]` として展開
- トピック概要を `**概要:**` に
- 詳細項目を `**ディスカッション:**` に箇条書き
- 原文で合意を確認できる事項だけを `**決定事項:**` に記載し、未確認の提案は区別する。

### 3. 持ち帰り事項

「フォローアップ タスク:」を振り分け：

| 担当者キーワード | 分類            |
| ---------------- | --------------- |
| 自社メンバー名   | 自社 持ち帰り   |
| 顧客側と確認済み | お客様 持ち帰り |
| 所属・担当が不明 | 要確認          |

### 4. 顧客共有用ハイライトブロック

顧客共有が許可された議事録にだけ、内部用 `## 次のアクション (社内メモ)` と別に `## お客様共有用ハイライト (コピペ用)` を 1 つ入れる。社内準備会や内部限定のワークスペースでは作らない。共有可否は会議名やファイル名でなくワークスペースの共有境界とユーザー指定で判断する。

構成:

- 冒頭 1 行 (例: 「本日はお時間いただきありがとうございました。以下、本日ミーティングのハイライトと次アクションをお送りします。」)
- `### 本日の主な確認事項`: 3〜5 bullets で決定事項と方針をサマリ
- `### 次アクション` を 3 バケットに切り分ける:
  - **お客様側**: 顧客側だけで進むタスク
  - **自社側**: 自社側だけで進むタスク
  - **双方 (両者で調整)**: 日程調整 / 共同レビューなど両者協力が必要なタスク。**お客様側 / 自社側に重複させない**

ルール:

- 共有用は確認済みの決定・合意・実績だけで埋める。内部推測や `要確認` は入れない。
- 内部ファイルパス、ワークスペース内リンク (`_customer/`, `_meetings/`, `next-actions/` 等) は含めない。
- **担当者の名前表記は `会社名 (姓)` 形式を默認にする** (例: `Microsoft (山本)`, `パートナー名 (沼尻)`)。内部 handle / first name (`Tatsumi` など) やエンゲージメント内の肊書き (`Azure CSA` など) は顧客共有ブロックに入れない。顧客側は「さん / 様」付けを保持する。

### 5. 品質ゲート

- 音声書き起こしは、**短い技術略語 / 時間単位 / エンゲージメント名 / 固有名詞**を特に聞き違える。例: `2H` が `EDE (Enhanced Delivery Engagement) 時間`、`SES` が `CES` / `SES`、`Entra ID` が `エントラID` になるなど。文脈と合わない短いトークンは推測で確定せず、ユーザーに確認するか `要確認` で残す。
- AI が抽出した持ち帰りは取得できた文字起こしと照合し、その範囲（または未取得）を記録する。部分取得は全体の確認とせず、根拠のない担当・期限・成果物は `要確認`。次回日時から締切を補ったり、時間次第の案を実施確約にしたりしない。
- `blocked` の持ち帰りには **ボール（どちら側の返答待ちか）と次の遷移条件** を書く。
- 催促連絡や返信待ちのような成果物を伴わない経過は `next-actions/` に残らないため、議事録末尾の追記セクションに `日付 / 内容 / 担当 / 次のアクション` の 1 行で残す（会議時点の決定事項・持ち帰り表は書き換えない）。再連絡が前提なら再連絡条件も書く。
