# Reconciliation Checklist

Prompt から Skill への移行後に、旧前提を探して分類するための観点。

## 検索パターン

大文字小文字を区別せず、バックスラッシュ区切りも対象にする。

- パス: `.github/prompts`、`*.prompt.md`、旧 Prompt のファイル名（拡張子なし）
- 動詞句: 「prompt を読む」「prompt に従う」「prompt を参照」「対応する prompt」
- 役割の自称: 「task-specific prompt」「この prompt」
- 正本の宣言: 「workflow は prompts を正とする」
- 図・一覧: フロー図のノード名、Dependencies 一覧、README の収録内容・使い方、Skill / agent 一覧
- 表の Entry 列・ルーティング表の旧ファイル名（`x.prompt.md`、`x_y` 形式の旧名）
- 呼び出しの書き方: `/prompt X`、「`/prompt` で追記」などの利用ヒント、スクリプトが出す次手順の表示文
- 見出し・表の列名: 「他プロンプトとの連携」「プロンプト」列、「この Prompt が更新するもの」
- 旧名は綴りが変わる: Skill 名はフォルダ名（ハイフン区切り）に揃うため、`_` 区切りの旧名で検索し、置換後は `-` 区切りの名前が実在することを確認する

## 検索の実行方法

- ワークスペース全体への grep は、同期フォルダ（OneDrive 等）や仮想環境で時間切れになる。現行資産のディレクトリ（`.github`、ルート直下、`scripts`、設定・データ置き場）に絞り、`.venv`・`node_modules`・生成物・`dist` を除く。最終の再検索も同じ範囲で行い、打ち切られた結果は網羅の根拠にしない
- 列挙したファイルを `Select-String` で検索する方式は、検索ツールが打ち切られても完走する

## 自動実行タスク（Scheduler・cron・CI・hook）

- 文面はタスク定義の中に保存され、ファイル検索に出ない。タスクの一覧で対象ワークスペースのものを絞り、詳細で文面全体を読んで旧参照を探す。他ワークスペースのタスクは対象外
- 一覧のプレビューは途中で切れており、書き戻さない。更新は文面全体の置換になるため、詳細で取得した全文を元に、旧参照だけを差し替える
- 旧 `x.prompt.md` を読んで従う形は、`.github/skills/x/SKILL.md` を読んで従う形へ置換して実行方式を保つ。`/x` で Skill を直接起動する形への変更は挙動が変わるので要判断
- 更新後は詳細を読み戻し、旧参照が無いこと、cron・有効状態・model・実行モード・紐付けが更新前と同じことを確認する。次回実行での動作は、実行されるまで未確認と報告する

## 検索範囲

- instructions、`AGENTS.md`、`copilot-instructions.md`
- agents（`.agent.md`、templates）、chat modes
- README、docs、Skill の一覧・カタログ
- Skill 本文（`SKILL.md`、references）
- スクリプトの実行処理・生成テンプレート・出力先・その利用側、および docstring・コメント・設定ファイル

履歴記録（議事録、作業ログ、過去回のメモ）は検索結果に出ても、原則として修正対象にしない。

## 分類の目安

| 状況 | 扱い |
| --- | --- |
| 現行の手順で「この Prompt を読む」と案内している | 修正（対応する `SKILL.md` へ） |
| 「正本は prompts」と宣言している | 修正（Skill を正本に） |
| 過去の議事録に旧パスが書かれている | 保持（履歴） |
| 日付付きの月次記録の先頭にある利用ヒント、実行ログ内のリンク | 保持（履歴）。テンプレートを生成する側の文面は修正 |
| 設定・データファイルの note が旧パスを指している | 修正（現行の参照） |
| 旧型ワークスペースを検出する・生成しないことを検証する処理 | 保持（検出が目的） |
| 旧名をプレースホルダー検出の文字列として持つ検査処理 | 要判断（既定は保持。変えると検査と生成済み下書きの扱いが変わる） |
| Skill が手動呼び出し専用なのに、instructions が「自動で実行」と書いている | 要判断（設定は変えず、`/名前` 案内か SKILL.md を読んで実行する表現へ寄せる） |
| LLM に渡す入力文という意味の「プロンプト」 | 保持 |
| Prompt 機能一般の説明（比較表など） | 保持 |
| 移行先 Skill が複数候補、または存在しない | 要判断 |
| 手動呼び出し専用などの挙動設定に関わる | 要判断（変更しない） |

## Skill 側の確認

- `name` がフォルダ名と一致し、移行元の用途が分かる名前になっている
- `description` に「何をするか」と「いつ使うか」がある
- 移行ツールが追加した設定（手動呼び出し専用など）の意味を報告し、変更は承認を取る
- 本文が自身を「prompt」と呼んでいないか（「このプロンプト」、見出し、表の列名を含む）
- Skill 一覧に載っている。自動生成ブロックがある場合は、そのブロックの外側に追記する。ブロックが一部の Skill しか含まない場合も、移行した Skill の一覧を外側に足す

## 編集時の注意

- 改行: 移行ツールが frontmatter だけ LF、本文を CRLF で書くことがある。この混在は既存状態なので崩れに数えず、編集前後で CRLF 行数と単独 LF 行数を比較する。複数行の置換は新しい行を LF で書くため、CRLF ファイルでは 1 行単位の置換にする。行の追加が必要で LF が混入した場合は、戻せないことを報告する
- 表: 列幅を揃えて整形された表は、置換後も区切りの位置を保つ
- 触った範囲に、移行と無関係な既存の文字化け（U+FFFD など）が見つかったら、依頼が無い限り直さず別項目で報告する

## 検証の型

1. 旧パス・拡張子の再検索で、修正対象のヒットが 0 件であり、残りが保持分だけであること
2. 修正後に書いた Skill パスが、すべて実在すること
3. 変更ファイルの改行・文字コードが元と一致し、空白エラーがないこと（CRLF 行数と単独 LF 行数の前後比較）
4. 呼び出し設定と元の担当 agent・tool 権限・承認境界が保たれ、未対応 frontmatter やインライン実行で代替していないこと
5. 実機での呼び出し確認（`/名前` の表示など）は、行っていなければ未確認と報告すること
6. 生成処理がある場合は使い捨ての作業先で実行し、現行ホスト用の入口と参照先が生成され、旧 Prompt 依存が再作成されないこと。モデルへ渡す通常の入力文・互換性説明・負例テストは除外する
